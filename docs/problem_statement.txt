Business Context / Problem
Trace affected lots through suppliers, production, warehouses and customers, then simulate recall scope and completion.

Objective and Scope
Build a working solution for this end-to-end workflow: Trace affected lots through suppliers, production, warehouses and customers, then simulate recall scope and completion. The solution should expose key decisions and exceptions, preserve traceability, and produce measurable outputs. Medium complexity means multiple related entities, conditional rules, at least one exception path and meaningful evaluation metrics.

Primary Actors / Systems
Supplier, planner, carrier/warehouse operator, logistics analyst and operations manager

Business Workflow and Rules
1. Generate/reference master data first: Supplier, MaterialLot, Product, BOM, ProductionOrder.
2. Generate dependent transaction/event records using valid parent IDs.
3. Apply business logic: Create raw material lots; consume lots into production orders/BOMs; generate finished lots; distribute finished lots through shipments to customer deliveries; create recall triggers for selected raw/finished lots; traverse genealogy downstream; track notifications, quarantine and recovered quantities.
4. Persist state changes as explicit records/events where relevant; do not overwrite history.
5. Generate outcomes and ground-truth labels from documented rules, not independent random assignment.

Entities and Relationships
Core entities: Supplier, MaterialLot, Product, BOM, ProductionOrder, FinishedLot, Shipment, Customer, Delivery, RecallCase, RecallAction. Define a primary key for every entity and foreign keys for every relationship. Document cardinality (1:1, 1:N, N:M), optional relationships, effective dates and lifecycle states. Use bridge tables for many-to-many relationships; retain event history for state changes; validate all joins. For deliberate anomaly cases, keep an issue_type/ground_truth label rather than silently corrupting unrelated rows.

ID / Nomenclature Conventions
RAWLOT-<supplier-id>-2026-000001; WO-2026-000001; FINLOT-2026-000001; SHP-2026-000001; REC-2026-000001.

Synthetic Data Generation Instructions (Granular)
Step 1 — Write a data dictionary for: Supplier, MaterialLot, Product, BOM, ProductionOrder, FinishedLot, Shipment, Customer, Delivery, RecallCase, RecallAction. For each field specify type, required/optional, allowed values, units, uniqueness and validation rule.
Step 2 — Create parent/master tables first, then child and event tables. Apply this domain-specific generation logic: Create raw material lots; consume lots into production orders/BOMs; generate finished lots; distribute finished lots through shipments to customer deliveries; create recall triggers for selected raw/finished lots; traverse genealogy downstream; track notifications, quarantine and recovered quantities.
Step 3 — Apply deterministic IDs and naming: RAWLOT-<supplier-id>-2026-000001; WO-2026-000001; FINLOT-2026-000001; SHP-2026-000001; REC-2026-000001. Keep counters zero-padded, IDs immutable, and referenced IDs exactly consistent across files.
Step 4 — Generate the baseline volume: Generate 500 suppliers, 10,000 raw lots, 5,000 production orders, 8,000 finished lots and 20,000 deliveries. Inject selected contaminated lots with hidden labels. Use a fixed seed (e.g. 20261022) and parameterize scale so starter and full datasets use the same generator.
Step 5 — Generate valid baseline records first, then inject labelled edge cases: Finished lot references missing input lot; delivered quantity exceeds produced quantity; recall misses a downstream customer; recalled inventory remains available for sale.
Step 6 — Calculate derived values (totals, balances, scores, statuses and dates) from source records rather than generating them independently.
Step 7 — Produce a separate ground_truth.csv/json for known anomalies, expected decisions or labels; never leak it into input features.
Step 8 — Run validation: primary-key uniqueness, foreign-key integrity, allowed enums, date ordering, arithmetic reconciliation, lifecycle transitions and duplicate checks.
Step 9 — Export CSV/JSON/SQL seed data plus README, schema/data dictionary, generator command, fixed seed, source manifest and validation summary.
Step 10 — Regenerate twice with the same seed and compare row counts/checksums to demonstrate reproducibility.

Validation Rules / Acceptance Criteria
Genealogy traversal is complete; quantities reconcile through production and distribution; recall scope matches planted source lots; actions track affected quantity and disposition.

Evaluation Focus for Generated Data
Review: (a) realistic distributions and meaningful variation; (b) consistent IDs and valid joins; (c) dependency/lifecycle consistency across entities; (d) correct derived values and reconciliation; (e) normal, boundary, failure and exception coverage; (f) separate ground truth; (g) fixed-seed reproducibility, documentation and lawful provenance.

Public Data Guidance / Lawful Use
External data is optional. If used, record source URL, dataset/version, retrieval date, license/terms, attribution, transformations and fields discarded. Use only data you are legally permitted to access and redistribute; do not bypass access controls or collect confidential/personal information. If licensing or suitability is unclear, use synthetic data and cite public reference data only for schema inspiration.
