# Recall traceability: synthetic dataset and recall simulator

Synthetic data for a food manufacturer: suppliers, raw lots, production, finished lots, shipments,
deliveries, and recall cases with every action taken. Everything is generated by code from a fixed
seed. No external data and no personal data are used.

## Generate and verify

```
python -m recallsim generate --seed 20261022 --scale starter --out <output-dir>
python -m recallsim verify --seed 20261022 --scale starter
```

`verify` generates twice in two separate Python processes and compares the SHA-256 of every file.

Seed: `20261022`. Scale: `starter`. As-of date: `2026-11-01`.
Needs Python 3.11 or newer, standard library only (pytest for the tests).

## What is in this folder

| Path | Content |
|---|---|
| `csv/`, `json/`, `sql/seed.sql` | The shipped dataset (with planted anomalies), 12 tables |
| `csv_clean/` | The same data before the anomalies were planted, for diffing |
| `ground_truth/` | Labels for the planted anomalies and the clean recall answer key. Never use as input. |
| `validation/` | Validator output for the shipped data and for the clean data |
| `metrics/` | Recall metrics: scope precision and recall, completion, time to notify |
| `sql/schema.sql`, `docs/DATA_DICTIONARY.md` | Schema and data dictionary, both generated from one schema file |
| `manifest.json` | Seed, counts, provenance, SHA-256 and size of every data file |

## Known limitations

- Supplier country is not linked to the origin of the materials.
- Very few deliveries are IN_TRANSIT, because every finished lot is older than a week at the as-of date.
- Recall blast radii are small compared with real incidents, and most cases close.
- There is no warehouse table, only a warehouse code on each shipment.
